Как связать Admin + Supplier + Buyer

Вот здесь надо строить не три кабинета, а одну матрицу видимости.

Пример: Order

Один и тот же Order:

В админке:
полный статус
источник
payment/integration данные
supplier attribution
buyer info
internal notes
refund workflow
audit info
В supplier cabinet:
только если order относится к supplier
только релевантные поля
без лишних внутренних деталей
видно продажу, сумму, статус, maybe buyer contact по правилам
видно refund status, если касается их продажи
В buyer account:
только заказы самого пользователя
статус
что куплено
дата/время
билет/ссылка
возврат/обращение

То же самое для RefundRequest:

admin обрабатывает
buyer подаёт и отслеживает
supplier видит, что по его событию есть такой кейс, если это нужно по бизнесу

9. Что отдавать Lovable, а что нет

С учётом ваших обсуждений:

В Lovable можно отдавать:
для frontend-admin
shell
navigation
list/detail scaffolding
filters
tabs
forms
dashboards
для frontend-supplier
shell
dashboard
my events
my orders
reports
integration status pages
support/profile flows
Не отдавать Lovable как свободную зону:
backend design
source-of-truth rules
auth model
permissions
order projection logic
refund workflow rules
import/sync engine
payout/finance engine
customer account data rules

То есть Lovable делает экран, а не архитектуру платформы.

10. Как строить связь с ЛК покупателя технически

Это важный кусок, который ты напомнил правильно.

По вашим прошлым решениям у тебя уже логика в нужную сторону:

OrderProjectionService
проекции заказов из internal checkout
проекции заказов из external mirrors / email / provider data
единый Order как центральная сущность

Дальше из этого следует:

Buyer account не должен зависеть от канала продажи

Покупателю всё равно, заказ:

через внутренний checkout,
через Ticketscloud mirror,
через Teplohod,
через другой API.

Если заказ удалось привязать к пользователю/почте/аккаунту, он должен оказаться в buyer account как нормальная запись.

То есть buyer account строится не вокруг payment provider, а вокруг:

userId
email/phone match
order identity
entitlement/ticket visibility

12. Мой итог по сути твоего вопроса

С учётом всех ваших прошлых обсуждений модель должна быть такой:

Backend

единый core:

source-aware events
unified orders
supplier attribution
customer linkage
refund requests
role-based projections
Admin

полный операторский слой платформы

Supplier cabinet

отдельный фронтенд, supplier-scoped, source-aware

Buyer account

клиентский контур, лучше внутри public frontend, order-centric

Lovable

использовать для frontend-admin и frontend-supplier как генератор интерфейсной поверхности

Cursor

использовать для интеграции, нормализации, контрактов, state, permissions, rollout
